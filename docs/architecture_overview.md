# دليل المعمارية الشامل للمنصة الأكاديمية (Academic Platform Architecture Guide)

هذا المستند يوثق المعمارية الفعلية، والقرارات الهندسية، وقيود قاعدة البيانات، وآليات التشغيل للمشروع.

## 2. قواعد ومحددات قاعدة البيانات (PostgreSQL 18 Invariants)

يلتزم المشروع التزامًا صارمًا بالضمانات المفروضة على مستوى قاعدة البيانات:
1. **التحقق من إجماليات الطلب (`trg_orders_totals_validate`):**
   - يُنشأ الطلب في حالة `draft` بإجماليات صفرية `subtotal_minor = 0, total_minor = 0`.
   - بمجرد إدراج بنود الطلب في جدول `order_items`، يُفعّل المشغل `trg_order_items_totals` دالة `recalculate_order_totals()` لحساب المجموع الفعلي وتحديث الطلب وتثبيت حالته للانتقال إلى `pending_payment`.
2. **مطابقة الدفع والطلب (`trg_payment_matches_order`):**
   - يمنع إنشاء معاملة دفع إذا كان المبلغ أو العملة أو معرّف المستخدم لا يطابق بيانات الطلب بدقة متناهية.
3. **التحديث التلقائي لحالة السداد (`trg_payment_success_paid`):**
   - فور تحول المعاملة المالية إلى `succeeded`، يُحدث المشغل حالة الطلب المقترن مباشرة إلى `paid` مع تعيين تاريخ السداد `paid_at`.
4. **حماية التضارب الزمني للحجوزات (`ex_bookings_provider_no_overlap`):**
   - قيد استبعاد `EXCLUDE USING gist` يمنع برمجيًا وتقنيًا حجز أي موعدين متداخلين لنفس مقدم الخدمة، مما يمنع race conditions تمامًا.
5. **سجل التدقيق المقفل (`audit_events`):**
   - جدول ملحق فقط (Append-Only) لا يسمح بأي عمليات `UPDATE` أو `DELETE` لضمان الشفافية والأمان والامتثال.

## 3. صندوق الإرسال التبادلي (Transactional Outbox Pattern)

لضمان موثوقية العمليات بين قاعدة البيانات وتيليجرام والخدمات الخارجية:
- تُسجل المهام داخل نفس المعاملة المصرفية/الأكاديمية في جدول `transactional_outbox`.
- يلتقط العامل الخلفي (`task_worker`) الدفعات المعلقة باستخدام استعلام:
  `SELECT ... FROM transactional_outbox WHERE status IN ('pending', 'retry') AND available_at <= now() FOR UPDATE SKIP LOCKED;`
- يوفر ذلك توازيًا آمنًا عبر عدة عمال بدون أي تكرار أو تنازع (Zero Locking Conflicts).
- تدعم المعالجة التراجع الأسي (Exponential Backoff) وقفل المهام الفاشلة بعد 5 محاولات في حالة `dead_letter`.

---

## 4. نظام الكاش الاختياري (Zero-Redis Degradation)

- صُمم النظام ليعمل بكفاءة 100% سواء كان Redis مفعلاً أو معطلاً عبر متغير `REDIS_ENABLED`.
- عند ضبط `REDIS_ENABLED=false`، يتحول `CacheService` تلقائيًا إلى وضع التشغيل المباشر من قاعدة البيانات، دون إبطال أي وظيفة حيوية ودون إلقاء استثناءات غير متوقعة.
- عند تفعيله، يستفيد النظام من التخزين المؤقت للكتالوج والبيانات الثابتة وتحسين زمن الاستجابة.

---

## 5. سياسة النزاهة الأكاديمية (Academic Integrity Policy)

تتضمن خدمة `ServiceRequestService` فلاتر تعبير نمطي (Regex Engine) صارمة لفحص نصوص الطلبات والاستفسارات:
- حظر طلبات حل الاختبارات الرسمية والكويزات المباشرة.
- حظر الغش نيابة عن الطالب أو إنجاز الواجبات دون مسار تفكيك المفاهيم.
- عند اكتشاف مخالفة، يُرفع استثناء `AcademicIntegrityViolationError` ويوجه الطالب إلى الأدوات البيداغوجية المعتمدة (شرح خطوات الحل، التدريب على مسائل مماثلة، جلسات الاستذكار).
